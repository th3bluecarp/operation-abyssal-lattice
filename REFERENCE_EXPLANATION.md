# Operation Abyssal Lattice — Reference Explanation

The intended solution is hard because the evidence contains two coordinated entry paths and several plausible distractions. The analyst should not begin by forcing every alert into one story. The defensible method is to normalize time, establish identities and asset ownership, build each chain independently, and then look for a cross-track control point.

Track A begins with the board-portal lure on `FIN-WS22`. The local browser and endpoint records normalize to the same UTC interval as DNS, proxy, Zeek, Suricata, and NetFlow. Okta then records session activity from `45.83.64.19`, including new geography/ASN and session-cookie reuse. OAuth consent and SaaS audit records show `Docs Sync Service` receiving delegated access and using it against specific board, mail, OneDrive, and Drive objects. This supports session/OAuth compromise and named-object confidentiality impact, but not password theft or tenant-wide access. The `a.velasquez` MFA denial is a blocked expansion attempt.

Track B begins with `build-linker@1.1.7`. Versions 1.1.0–1.1.6 establish benign package history; 1.1.7 adds the lifecycle script observed by npm and endpoint logs. The shell retrieves attacker infrastructure, accesses the GitHub credential path, stages metadata, and installs LaunchAgent persistence. GitHub audit then shows the same infrastructure controlling `r.kapoor`, briefly adding a deploy key, and pushing the unprotected `hotfix/cache-key` ref. The changed reusable workflow downloads and executes remote Python during approved run 8841.

The CI job receives an OIDC token for the unusual hotfix subject. Legitimate `release-orchestrator` assumptions of the same `gha-release-role` from `refs/heads/main` exist in the weekly baseline, so the finding is the mutable ref combined with wildcard trust—not the mere existence of the role. The role reads the production kubeconfig and creates `partner-export-sync` in `prod`. The pod's `release-exporter` service account assumes `eks-prod-exporter`, reads `/prod/export/box_token`, gathers the two logged inputs, creates `regulated_delta.7z`, and uploads it through the prod NAT address.

Box is the convergence point. The same `45.83.64.19` used in Track A probes and then fully downloads the exact archive created by Track B. Upload completion precedes link creation; link creation precedes both retrieval requests. The complete object remains 94,513,012 bytes across pod and Box evidence. The larger 99,514,862-byte network flow includes bidirectional TLS/network overhead and reconciles exactly with the Zeek byte counters. Exfiltration is therefore confirmed.

Three other clusters require separate treatment. `m.sato`'s `board_packets.7z` creation and internal file-share copy reconcile with FIN-1842 and never reach an external destination. `j.mercer`'s XMRig execution is a real, separately containable incident with its own VPN, endpoint, GCP, DNS, and mining-pool network chain. The PT-07 lookup comes from an old retry file and systemd path activation tied to the February authorized exercise.

Two uncertainty boundaries matter. `gha-release-role` could read broadly under `/prod/*`, including parameter names related to release signing, but the supplied KMS/workflow evidence contains no signing operation. Separately, the 17:18:07Z event-selector change narrows later S3 object visibility. The actor and timing do not prove attacker control, so a correct report treats the change as a scope gap rather than anti-forensics.
